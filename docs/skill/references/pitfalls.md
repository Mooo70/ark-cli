# 实测证伪清单：别再花第二次冤枉钱

这个文件记录的都是**真机跑出来的结论**，不是推测。每条后面是「所以你应该怎么做」。

## 1. 接口会静默忽略不认识的参数

往生图请求体里塞 `__bogus_param__: 123`，照样返回 200 并出图。

**所以：「没报错」不等于「生效了」。** 任何参数都必须用产物验证，不能靠「接口接受了」来判断。这条是所有踩坑的根源——它让错误假设活得特别久。

验证方法：同一提示词，参数取 A / B 两个值，各跑一次，比对产物的 sha256 或肉眼差异。两次结果一致 = 参数没生效。

## 2. `seed` 锁不住构图

同 seed 连发两次，图片 sha256 完全不同。

**所以：不做 seed 控件，不承诺可复现。** 视频侧官方文档写了 seed 可复现，但既然生图侧实测反例，就别在 UI 上给用户这个心理预期。要稳定出图，靠提示词写得足够具体 + 参考图，不靠随机种子。

## 3. `max_images` / `sequential_image_generation` 只要 1 张

新旧两种写法都试过，`data` 数组长度恒为 1。

**所以：「要 N 张」= 客户端连发 N 次。** 代价是耗时线性增加、计费按次叠加。第一次就失败要立刻抛出停止——否则是配置问题（没开通/参数非法），继续发只是白烧钱。

实测：`count=2` 真出 2 张，费用 2 × 单价。

## 4. `output_format: png` 对 4.0 是硬错误

4.0 传 png 直接 400 `not supported by the current model`。png 只有 5.0 系列支持。

**所以：格式开关要按模型能力表判断，不要在 UI 上给所有模型都摆一个 png 选项。** 能力表里 `formats` 字段就是干这个的。

## 5. Model ID 会悄悄下线

`doubao-seedream-4-0-250828` 已下线，请求 404；当前主线是 `doubao-seedream-4-0-20260415`。

**所以：404 的提示里必须同时说三种可能**——模型不存在 / 账号未开通 / ID 已下线。只写「模型不存在」会让人去改代码，而真正原因是没开通。

再往前一步：**把 404 变成一次学习**。网页端在收到 404 后把该模型标记为「未开通」（持久化在 `localStorage` 的 `ark.image.unavailable.v1`），下拉框显示标记，并自动切到下一个可用模型；模型成功出图一次就自动去掉标记。用户只需撞一次墙，而不是每次打开都撞。

## 6. 挂参考素材时 1080p 不可用

给参考图/参考视频时选 1080p 会失败，480p / 720p 正常。文档没明写。

**所以：分辨率校验要感知「有没有参考素材」**，不能只看模型能力表。报错信息要直接建议降到 720p。

## 7. `reference_video must be provided as a web url`

本地视频走 base64，就算没超 64MB 上限，服务端也只认公网 URL。

**所以：参考视频/音频一律走对象存储直链。** 不要在本地路径、`file://`、base64 之间反复试——它们都不行。这是产品约束，不是 bug。

同理，**选素材托管方案要第一个验证**：它决定「能不能用」，而不是「好不好用」。当时先花时间试本地直传、试隧道，最后才上对象存储，完全是顺序错了。

## 8. 改了代码页面没反应（八成是连到了另一个进程）

ESM 没有热重载；旧的 Node 进程还在跑，端口被它占着，新进程要么起不来、要么起了但浏览器连的是旧的。

**最阴的一种情况：端口被占时静默 `+1` 并自动打开浏览器。** 于是你在 5200 上对着一个 14:07 启动、模型表里只有 4 个模型的旧进程，
而新代码在 5199 上跑着——页面看起来"功能是新的、数据是旧的"，因为 `index.html` 每次从磁盘读、`models.js` 只在启动时进内存。
这时去翻前端代码会一无所获。

**正确的做法（已写进基线的 `startServer`）：**

1. 端口被占时先 `GET /api/state` 探测占用者是不是 ark 自己；
2. 是 ark → **打印它的地址、pid、模型数量后直接退出**，不再起第二个进程，也不把浏览器带到别的端口；
3. 是别的程序 → 明确打印「端口 X 被其他程序占用，改用 Y」，不静默；
4. `/api/state` 下发 `pid` 与 `startedAt`，页面「运行状态」卡片显示 `地址 · pid · 启动时间`。

**排查顺序**：先看页面那行「实例」，再看 `curl /api/state` 的 `pid` 和模型数量，最后才怀疑代码。

## 9. 别靠远看截图猜 UI 细节

缩略图下方的编号是 `r1 / r2 …`（reference 的序号），不是 `1 / 2 / 3 / 4 / 5`。远看像数字，放大才发现是 rN。

**所以：截图里的标签、编号、图标，放大确认再下结论。** 基于误读提出的「改进建议」会让用户直接失去信任。

## 10. 口算差价会错一个数量级

曾把 480p→1080p 的差价说成「约 ¥2」，实际 12 秒的差价约 ¥37。

**所以：任何价格结论都写下来算一遍**（单价 × 秒数），不要用「感觉差不多」应付。

## 11. 预设与显式参数打架

用户选了预设又手动改了参数，谁赢？

**结论：显式写的 flag 永远赢。** 预设只负责填空。这条要写进校验函数的最前面，并在日志里说明「预设改了哪几项」，否则用户会以为预设没生效。

## 12. 控制台显示「已开通」，本地下拉里却找不到

「开通」是账号权限，「出现在界面上」是本地模型表有没有这一条——两者完全独立。

真实案例：用户开通了 `Doubao-Seedream-5.0-flash`，控制台一片绿，下拉里却没有。原因不是没开通，
而是 `IMAGE_MODELS` 里只写了 lite 和 pro，漏了 flash；而且 5.0 三条线是**独立产品**，ID 各不相同：
`-5-0-flash-260915` / `-5-0-pro-260628` / `-5-0-260128`。

**所以要做两层兜底**：

1. 模型表按官方「模型列表」页逐条对齐，含 ID、档位、格式、是否组图、单价
2. UI 必须留一个「＋ 自定义 Model ID」出口，让用户填完整 ID 就能用（`resolveImageModel` 对未知 ID 原样透传）

没有第 2 层，模型表就永远在追赶厂商的新模型，每上线一个都要改代码。

## 13. 有些参数是硬错误，不是静默忽略

`sequential_image_generation: "disabled"` 在 4.0 上完全正常，在 5.0 pro / flash 上直接：

```
400 The parameter `sequential_image_generation` specified in the request are not valid:
    the parameter is not supported by the current model
```

注意它连「关闭」这个值都不接受——不是语义问题，是**整个字段不被该模型认识**。

**所以：可选字段要按模型能力决定「带不带」，而不是「带什么值」。** 在模型记录里放一个 `group: true/false`，
组包时 `group === false` 就整段省略。这条规律对任何「能力开关型参数」都成立（输出格式、组图、音频……）。

## 四条方法论（比具体结论更值钱）


1. **先验证最贵的假设。** 「能不能传上去」比「传上去好不好用」贵得多。托管方案、鉴权方式、模型是否开通——这些属于「不行就全盘推翻」的假设，必须第一个测。
2. **一次只改一个变量，用产物比对。** 接口静默忽略参数，只能靠结果差异判断生效与否。
3. **先花 2 块钱验证，再花 200 块批量。** 最便宜的验证组合（480p / 1K / 单张）就能证明链路通不通。
4. **写完就自检，不要攒着。** `--selftest` 每加一个功能就补一条断言；攒到最后补，等于没补。
